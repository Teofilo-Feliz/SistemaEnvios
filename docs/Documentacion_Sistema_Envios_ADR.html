Sistema de Envíos ADR

Documentación funcional, técnica y de base de datos

Versión consolidada · 31 de agosto de 2026

Sistema logístico para el control de equipos, envíos, transportación, recepción y revisión tecnológica.

1. Resumen ejecutivo

El Sistema de Envíos ADR administra el ciclo de vida de equipos enviados entre filiales y el Centro Sede de Tecnología. Registra trazabilidad, responsables, transporte interno o privado, confirmaciones por rol, recepción de equipos, incidencias y notificaciones.

Principios: trazabilidad completa, estados controlados por transiciones, validación de tickets, separación de responsabilidades y conservación histórica de catálogos.

2. Arquitectura

  • Frontend: Vue 3, Vite, Vue Router, Pinia, Axios, SweetAlert2 y componentes reutilizables.
  • Backend: ASP.NET Core, arquitectura por capas (API, Application, Domain, Infrastructure), FluentValidation y Entity Framework Core.
  • Persistencia: SQL Server, esquema versionado mediante scripts y restricciones de integridad.
  • Autenticación: Auth Manager externo; en desarrollo existe DemoAuth. El token aporta sub y permisos.
Frontend → API REST autenticada → Servicios de aplicación → EF Core → SQL Server

4. Flujo funcional

Crear envío → En filial → Entregado a transportación → Pendiente confirmación → Confirmado por transportación → En tránsito → Espera Tecnología → En revisión → Recibido por Tecnología

Transporte interno

Se selecciona un chofer activo del catálogo. Al entregar el envío, queda pendiente de confirmación; Transportación confirma la custodia y luego confirma la llegada. Esa llegada cambia el envío a ESPERA_TECNOLOGIA y genera una notificación.

Transporte privado

Se registran nombre, parentesco, cédula y placa. La entrega privada pasa directamente a tránsito y la recepción posterior se gestiona hacia Tecnología, sin confirmación de custodia interna.

Confirmaciones y recepción

Todas las transacciones relevantes muestran SweetAlert2 antes de completarse. Tecnología recibe una alerta con contador, revisa el detalle de equipos y confirma la recepción antes de pasar a revisión.

5. Reglas de negocio y validaciones

  • El ticket es obligatorio, numérico y de 3 a 50 dígitos.
  • No se permiten dos equipos con el mismo ticket ni tickets repetidos entre envíos.
  • El frontend consulta disponibilidad del ticket antes de agregar el equipo; el backend vuelve a validarlo y la base contempla índice único.
  • El origen y destino deben ser una filial y Tecnología. Al seleccionar una filial, el destino se propone como Centro Sede Tecnología.
  • La edición del envío solo está disponible en estado EN_FILIAL; el backend aplica la misma regla.
  • Los choferes no se eliminan: se deshabilitan para conservar historial.
  • El transporte interno exige chofer activo; el privado exige datos completos.
  • Los cambios de estado deben existir en la tabla de transiciones y se registran en historial.
  • SweetAlert2 presenta advertencias, errores y confirmaciones de forma visible.

8. Base de datos y normalización

La estructura está en tercera forma normal para los datos operativos: los catálogos no se repiten en los hechos, las relaciones muchos-a-muchos se resuelven con tablas puente y los datos específicos de transporte se separan en tablas internas y privadas.

9. API

La API se organiza por recursos REST: /api/envios, /api/envio-equipos, /api/transportes, /api/recepciones, /api/equipos, /api/notificaciones, estados y catálogos. Las operaciones mutables requieren autorización por política.

10. Concurrencia, salud y pruebas

  • EF Core usa control de concurrencia mediante RowVersion en entidades operativas.
  • Las reservas e índices únicos protegen asignaciones simultáneas.
  • La API expone comprobaciones de salud para aplicación y SQL Server.
  • La paginación limita carga de listados y la consulta de notificaciones limita a 100 pendientes.
  • Se ejecutaron 19 pruebas automatizadas del backend: 19 aprobadas, 0 fallidas.
  • El frontend se valida mediante compilación Vite.

11. Instalación y operación

  1. Configurar ConnectionStrings:SistemaEnvios mediante User Secrets o variable de entorno.
  2. Ejecutar el esquema SQL y las migraciones en orden.
  3. Backend: dotnet run --project SistemaEnvios.Api.
  4. Frontend: entrar a FrontEnd, ejecutar npm install y npm run dev.
  5. Copiar FrontEnd/.env.example a .env y ajustar VITE_API_BASE_URL.
  6. Verificar permisos del token y conectividad con SQL Server.

12. Mantenimiento recomendado

  • Aplicar migraciones en ambientes controlados y respaldar SQL Server.
  • Monitorear health checks, logs, bloqueos y tiempos de consulta.
  • Revisar periódicamente catálogos activos y duplicados históricos.
  • Agregar pruebas de integración para concurrencia de tickets y transición completa por cada modalidad de transporte.
